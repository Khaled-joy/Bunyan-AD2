# IMPORTANT INSTRUCTIONS FOR REPLIT

You are building interactive games inside the **Bunyan Abu Dhabi** platform.

Do not create simple static prototypes or mockups. Build **fully functional, playable games** with real game logic, level progression, age-based difficulty, timers, scoring, animations, and analytics event tracking.

Before starting development, carefully follow all requirements below.

---

## 1. FIRST: UNDERSTAND THE EXISTING PLATFORM

The games must feel like a natural part of the existing **Bunyan Abu Dhabi platform**.

Before designing any new components:

* Review the existing application's UI.
* Identify the existing color palette.
* Reuse the existing primary and secondary colors.
* Reuse existing typography where possible.
* Follow the existing border radius, button styles, cards, shadows, spacing, and layout.
* Do not create a completely different visual identity.
* Do not redesign the entire Bunyan platform.
* The games should look like they belong inside the same website.

If there are existing CSS variables, Tailwind configuration, theme files, or reusable UI components, use them instead of creating duplicate styles.

Create reusable game components that follow the existing design system.

---

# 2. BUILD THE GAMES AS A REUSABLE GAME SYSTEM

Do not build each game completely independently.

Create a reusable architecture that can support future Bunyan Abu Dhabi games.

The structure should separate:

### Game Engine

Responsible for:

* Starting games
* Ending games
* Pausing games
* Level progression
* Timers
* Difficulty management
* Age adaptation
* Scoring
* Rewards

### Game Content

Store questions, words, images, colors, and challenges separately from the UI.

Do not hard-code game questions directly inside React components.

Use configurable data structures.

For example:

* game configuration
* levels
* questions
* difficulty
* age ranges
* language
* rewards

Future administrators should be able to add or change game content without rewriting the entire game.

---

# 3. AGE ADAPTATION ENGINE

Create a reusable **Age Difficulty Engine**.

The system must adapt every game based on the player's age.

Supported ages:

**6 to 17 years old**

Use age groups internally, for example:

* Ages 6–8
* Ages 9–12
* Ages 13–15
* Ages 16–17

However, also use the player's exact age where appropriate to make gradual adjustments.

The game difficulty should not suddenly become much harder at one specific age.

The system should adjust variables such as:

* Game speed
* Number of distractors
* Question complexity
* Vocabulary difficulty
* Number of answer options
* Hint availability
* Time limits
* Object size
* Reading complexity
* Obstacle frequency
* Number of simultaneous tasks

Example:

A 6-year-old and a 17-year-old can both play **Color Focus Level 1**, but their Level 1 experience should not be identical.

The 6-year-old should receive:

* Slower speed
* Larger objects
* Fewer distractors
* More visual support

The 17-year-old should receive:

* Faster gameplay
* More distractors
* More difficult decisions
* More complex rule changes

---

# 4. THREE-LEVEL SYSTEM

Every game must have exactly three main levels:

## Level 1 – Easy

Introduce the game mechanics.

The player should understand:

* What to do
* What to collect or select
* How to interact

Provide more guidance and visual support.

---

## Level 2 – Medium

Increase the challenge.

Possible changes:

* Faster gameplay
* More options
* More distractors
* More complex questions
* Reduced hints
* More difficult interactions

---

## Level 3 – Challenging

Create the highest level of difficulty appropriate to the player's age.

Increase challenge without making the game unfair.

Possible changes:

* Faster speed
* More complex rules
* Multiple objectives
* Advanced vocabulary
* More distractors
* More challenging sequences
* Reduced assistance

---

# 5. ADAPTIVE DIFFICULTY

In addition to age adaptation, monitor the player's performance.

For example:

If the player is consistently performing very well:

* Gradually increase difficulty.
* Increase speed.
* Reduce hints.
* Introduce more challenging content.

If the player is struggling:

* Do not immediately end the game.
* Provide supportive feedback.
* Slightly reduce difficulty.
* Provide visual guidance.
* Offer hints where appropriate.

Do not make difficulty changes obvious to the player.

The game should feel natural.

---

# 6. ANALYTICS AND EVENT TRACKING

This is one of the most important requirements.

The games are part of Bunyan Abu Dhabi and must capture gameplay events for later analysis.

Create a reusable:

`AnalyticsService`

Every game must send structured events.

Use a common event format.

Example:

```javascript
{
  event_name: "item_resolve",
  timestamp: Date.now(),
  session_id: "...",
  player_id: "...",
  game_id: "color_focus",
  game_version: "1.0.0",
  level: 1,
  age_months: 96,
  age_band: "cycle1",
  language: "ar",
  device_class: "tablet",
  input_type: "touch",
  item_id: "color_blue_01",
  difficulty: 2,
  correct: true,
  custom: {}
}
```

The analytics system must be reusable across all games.

Do not create completely different event formats for every game.

---

## Required Session Events

Capture:

* `session.start`
* `session.end`
* `level.start`
* `level.complete`
* `game.complete`
* `game.abandon`
* `timeout`
* `focus.lost`
* `focus.returned`
* `idle.start`
* `idle.end`

Track the final session end reason:

* complete
* abandon
* timeout
* crash

Do not simply ignore abandoned sessions.

---

## Required Item Events

Depending on the game interaction, capture:

* `item.present`
* `first_input`
* `item.change`
* `item.submit`
* `item.resolve`
* `hint.request`

For drag-and-drop games also capture:

* `drag.start`
* `drag.move`
* `drag.end`

For Color Focus also capture:

* correct collect
* wrong collect
* obstacle hit
* jump
* slide
* lane change
* target color change

---

# 7. TIME MEASUREMENT

Measure timing accurately.

For every item or challenge, calculate:

### Hesitation Time

Time between:

`item.present`

and:

`first_input`

This represents the time before the player starts interacting.

---

### Deliberation Time

Time between:

`first_input`

and:

`item.submit`

This represents the time spent evaluating or changing the answer after starting.

---

### Total Time

Time between:

`item.present`

and:

`item.resolve`

Do not combine these measurements into one generic "response time".

Store them separately.

---

# 8. ITEM-LEVEL DATA

Where applicable, every challenge should capture:

* item_id
* item_ordinal
* attempt_number
* difficulty
* modality
* hesitation time
* deliberation time
* total completion time
* correct or incorrect
* number of answer changes
* changed to correct
* hint usage
* attempts before hint
* number of options explored
* selected option dwell time
* rejected option dwell time where technically possible
* off-task time
* repeated previous error
* moves used
* optimal moves
* strategy signature

Do not force variables that do not make sense for a specific interaction.

Use the appropriate data for the game type.

---

# 9. MOVEMENT TRACKING

For drag, swipe, and movement-based games, create optional reusable movement tracking.

When technically appropriate, calculate:

* gesture type
* duration
* path length
* straight distance
* directness
* number of reversals
* pauses
* total pause time
* peak velocity
* time to peak velocity
* number of zones entered
* near miss
* jitter

Do not permanently store unnecessary raw coordinates.

Prefer calculating useful movement features and storing the derived metrics.

Movement metrics must consider the player's input type:

* Touch
* Mouse

Do not directly compare movement metrics across different input types without preserving the input type in the event.
